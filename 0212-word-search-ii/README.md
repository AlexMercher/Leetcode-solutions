## Explanation

Understand the important optimization
The biggest change from normal Word Search II is this:
Brute-force idea
For every word:
word 1 → DFS board
word 2 → DFS board
word 3 → DFS board
...
30000 words

Terrible repetition.
Trie idea
             Trie
              |
       ┌──────┼──────┐
      eat    oath   rain

Then board DFS walks the Trie and the board simultaneously.
For example, starting from:
o

we check:
Trie root
   ↓
  'o' exists?

Then we move on the board to a neighboring character:
o → a

and ask:
Trie 'o' → 'a' exists?

If not, that entire board path dies immediately.
That's the huge pruning advantage.
Why wordIndex instead of string word?
Instead of every terminal Trie node storing:
string word;

we store:
int wordIndex;

For example:
words[7] = "oath"

Trie terminal node:
wordIndex = 7

Then:
answer.push_back(words[7]);

This avoids keeping/copying a separate string inside the Trie.
And after finding it:
trie[next].wordIndex = -1;

means:
"We already found this word; don't return it again."

So we don't need a set<string> afterward.
Why mask?
Exactly the same trick from the previous Trie.
Suppose this node only has:
a
e
t

Then:
mask

has only those three bits turned on.
This:
if((trie[level].mask & (1u << idx)) == 0)

means:
"Does this Trie node have this character as a child?"

And:
trie[level].child[idx]

gives the actual node number.
Why emplace_back()?
This:
trie.emplace_back();

constructs a new TrieNode directly at the end of the vector.
And:
trie.reserve(300001);

pre-allocates enough capacity so the vector doesn't repeatedly reallocate as the Trie grows.
So the pattern is:
reserve()
   ↓
give vector enough storage

emplace_back()
   ↓
construct new node directly in that storage

One important change from your previous optimized Trie
Previously:
uint16_t arr[26];

looks very attractive because it saves memory.
But here:
30,000 words × 10 chars
≈ 300,000 Trie nodes

and:
uint16_t max = 65,535

So uint16_t can overflow.
That's why here:
uint32_t child[26];

is the correct robust choice.
One more optimization worth noticing
We don't use:
vector<vector<int>> visited;

Instead:
board[r][c] = '#';

marks the current cell.
After DFS:
board[r][c] = ch;

restores it.
So we avoid allocating and accessing a separate visited matrix during every search.
The overall pipeline
words
  ↓
Trie
  ↓
board cell
  ↓
Trie transition
  ↓
neighbor
  ↓
Trie transition
  ↓
...
  ↓
wordIndex != -1
  ↓
found word

This is the important pattern for Word Search II:
Trie handles prefix pruning; DFS handles spatial paths.

The mask, integer node IDs, reserve, emplace_back, and in-place board marking are then constant-factor optimizations on top of that core algorithm.
