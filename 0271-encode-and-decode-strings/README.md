## Explanation

Take:

["Hello", "World"]
Encoding

First string:

"Hello"
length = 5

Add:

5#Hello

Second:

"World"
length = 5

Add:

5#World

Final encoded string:

5#Hello5#World
Decoding

Start:

s = "5#Hello5#World"
i = 0

Find #:

"5#"

So:

len = 5;

Read next 5 characters:

Hello

Add to answer:

["Hello"]

Move:

i = 7

because:

5#Hello
^^^^^^^
7 characters

Now we're at:

5#World

Again:

len = 5
string = "World"

Final:

["Hello", "World"]
Why does this work with # inside the string?

Suppose:

["ab#cd", "xyz"]

Encoding:

5#ab#cd3#xyz

At first, decoder reads:

5#

so it knows the next 5 characters belong to the first string:

a b # c d

The # inside the actual string doesn't matter.

Then it continues at:

3#xyz

So there is no ambiguity.

Empty strings also work

For:

["", "abc"]

encoding:

0#3#abc

Decoder sees:

0#

and reads exactly zero characters:

""

then:

3#abc

gives "abc".

Follow-up: arbitrary character set

This same idea is already generalized.

The important property is:

We don't use any character inside the string as a separator whose presence has to be forbidden or escaped.

We encode:

[length][separator][data]

The length tells us exactly how many bytes/characters belong to the data.

So even if the string can contain:

#
0
newline
spaces
commas
Unicode
binary bytes

the scheme still works, provided the length is measured consistently.

For a truly arbitrary byte sequence, you'd typically use a binary length prefix:

[4-byte length][raw bytes]

For example:

00 00 00 05 | H e l l o

Then the decoder reads 4 bytes to get the length 5, followed by exactly 5 bytes.

Pattern to remember

This is the important interview idea:

When serializing variable-length pieces, prefix each piece with its length.
string → length + delimiter + data
