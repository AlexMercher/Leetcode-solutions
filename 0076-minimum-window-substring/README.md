## Explanation

Take:

t = "ABC"

We need 3 characters total.

Suppose current window is:

"ADOBEC"

We have:

A → 1/1 ✅
B → 1/1 ✅
C → 1/1 ✅

So:

formed == required

and the window is valid.

Now we start shrinking from the left:

ADOBEC
↑

Remove A:

DOBEC

Now:

A → 0/1 ❌

So:

formed--

and the window is no longer valid.

That gives us the important rule:

Expand right → make window valid
Shrink left  → make valid window minimum
Why these conditions?

When adding:

if(need[c] > 0 && have[c] <= need[c])
    formed++;

Suppose t needs:

A = 2

and we currently have:

A = 1

Adding another A gives:

have[A] = 2

Now we've satisfied one more required character.

But if we add a third A:

have[A] = 3

we don't increment formed, because that third A is extra.

Similarly, when removing:

if(need[x] > 0 && have[x] < need[x])
    formed--;

we decrement only when removing that character causes the window to fall below the required count.

Dry run idea for "ADOBECODEBANC"
t = ABC

Eventually we get:

ADOBEC

valid → save length 6.

Shrink:

DOBEC

invalid.

Continue expanding and eventually:

BANC

is valid.

Its length is 4, smaller than 6, so answer becomes:

"BANC"

Minimum window = expand until valid, then shrink while valid.

And unlike the previous permutation problem, this is a variable-size sliding window.
