## Explanation

Think of stringstream as a string pretending to be a stream, like cin.
For your serialization problem, the serialized string is:
1,2,#,#,3,4,#,#,5,#,#

You want to read it piece by piece, using , as the separator.
1. stringstream
When you do:
stringstream ss(data);

you are essentially saying:
"Take this string and let me read from it like I normally read from cin."

So:
data
 ↓
"1,2,#,#,3,4,#,#,5,#,#"
 ↓
stringstream ss

Now ss has an internal reading position, initially at the beginning:
1,2,#,#,3,4,#,#,5,#,#
↑
current position

When you read something, the position moves forward.
2. getline
Normally:
getline(cin, str);

means:
Read characters until you hit a newline.

But getline has another form:
getline(stream, string, delimiter);

So:
getline(ss, val, ',');

means:
Starting from the current position in ss, keep reading characters until you hit ,. Put those characters into val.

For:
1,2,#,#,...

the first call:
getline(ss, val, ',');

gives:
val = "1"

and the stream position moves past the comma:
1,2,#,#,...
  ↑
  current position

The next call gives:
val = "2"

Then:
val = "#"
val = "#"
val = "3"
...

So you can think of:
getline(ss, val, ',');

as:
"Give me the next token separated by commas."

3. Mental model
Think of the string as a conveyor belt:
1 , 2 , # , # , 3 , 4 , # , # , 5 , # , #
↑

stringstream remembers where you currently are.
Every time you call:
getline(ss, val, ',');

it:
1. starts at the current position
2. reads until ,
3. stores that chunk in val
4. moves the current position after the comma
So:
Call 1 → "1"
Call 2 → "2"
Call 3 → "#"
Call 4 → "#"
Call 5 → "3"

You don't manually maintain an index. The stream does it for you.
4. Why getline instead of >>?
You might wonder:
ss >> val;

Why not that?
Because >> normally uses whitespace as the separator.
Your data is separated by:
,

not spaces.
For example:
"1,2,#,#"

>> doesn't naturally mean "split on comma."
getline lets us explicitly say:
getline(ss, val, ',');
                         ↑
                    separator

That's why it's perfect here.
5. Why does this work with #?
Because # is just another piece of text.
For:
1,2,#,#,3

we get:
"1"
"2"
"#"
"#"
"3"

Then:
if(val == "#")
    return nullptr;

So the string parser understands:
number → create node
#      → no node

6. One important behavior: last token
Suppose:
"1,2,3"

There is no comma after 3.
Still:
getline(ss, val, ',');

will return:
"3"

because getline also stops when it reaches end of stream.
So the mental model is:
Stop at the delimiter or at the end of the input.

7. How this fits your deserialize function
You had:
TreeNode* decode(stringstream& ss) {
    string val;
    getline(ss, val, ',');

    if(val == "#")
        return nullptr;

    TreeNode* root = new TreeNode(stoi(val));

    root->left = decode(ss);
    root->right = decode(ss);

    return root;
}

The first call:
data = "1,2,#,#,3,4,#,#,5,#,#"

gets:
val = "1"

Create node 1.
Then recursively call:
decode(ss)

The stream is already positioned after 1,.
So the next call gets:
"2"

Then the next:
"#"

Then:
"#"

etc.
That's why passing stringstream& ss by reference is important:
decode(stringstream& ss)

All recursive calls share the same stream and the same current position.
If you made a fresh stringstream every time, you'd keep starting from the beginning.
The mental model I'd use
Whenever you see:
stringstream ss(data);

think:
"I turned my string into a cin-like object."

Whenever you see:
getline(ss, x, ',');

think:
"Give me the next comma-separated piece and move the stream forward."

So:
"1,2,#,3"
 ↑
stringstream
    ↓
getline(..., ',')
    ↓
"1"
    ↓
stream moves
    ↓
"2"
    ↓
stream moves
    ↓
"#"

That's all stringstream + getline is doing here.
