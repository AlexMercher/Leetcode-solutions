## Explanation

Why are we storing ListNode* directly?
Because the nodes are already connected and already contain their values.
We don't need:
(value, list number, index)

We can just put the node pointer into the heap.
The comparator:
return a->val > b->val;

makes it a min-heap, so:
pq.top()

is the node with the smallest value.
Dry run
Start:
pq = [1(list1), 1(list2), 2(list3)]

Pop:
1

Attach it.
Push its next:
pq = [1(list2), 2(list3), 4(list1)]

Pop:
1

Push next 3:
pq = [2,3,4]

Pop 2, push 6:
pq = [3,4,6]

Then:
3
4
4
5
6

Final:
1 → 1 → 2 → 3 → 4 → 4 → 5 → 6

Why this is O(N log k)
Let N be the total number of nodes across all lists.
Every node:
- enters the heap at most once
- leaves the heap once
The heap contains at most k nodes.
So each operation costs:
O(log k)

and there are N nodes:
Time:  O(N log k)
Space: O(k)

The pattern to recognize is:
Multiple sorted sequences + merge them → keep the current smallest candidate from each sequence in a min-heap.

For a custom comparator, the rule is:
bool operator()(A a, A b)

return true when a should come after b in the priority queue's ordering.
For the min-heap of ListNode*:
struct Compare {
    bool operator()(ListNode* a, ListNode* b) {
        return a->val > b->val;
    }
};

Why >?
a = 5
b = 2

5 > 2 → true

So 5 has lower priority than 2, making 2 come to the top → min-heap.
How to write one
First ask:
Which one should have higher priority?

For a min-heap:
return a > b;

For a max-heap:
return a < b;

For objects, compare the required field:
struct Compare {
    bool operator()(Node* a, Node* b) {
        return a->value > b->value;   // min-heap
    }
};

Then:
priority_queue<Node*, vector<Node*>, Compare> pq;

Mental shortcut:
priority_queue default → largest on top
want smallest on top    → reverse the comparison

So for your linked-list problem: a->val > b->val

means smaller value gets higher priority.
