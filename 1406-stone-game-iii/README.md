# DP Learning Notes (Stone Game III)

## 1. Start with the **State**, not the DP Type

Don't begin by thinking:

* "Is this Interval DP?"
* "Is this Knapsack?"

Instead ask:

> **What is the minimum information required to describe the remaining problem?**

If only one variable changes, use 1-D DP. Only introduce more dimensions if they are truly needed.

---

## 2. DP State

A DP state should represent the **remaining problem**, not the history.

Think:

* What remains?
* What choices can I make from here?

Avoid thinking about what has already happened.

---

## 3. Separate Game Direction from DP Fill Order

These are independent.

* **Game direction** tells you the next state.
* **DP fill order** is chosen only to satisfy dependencies.

Never use `i-1` just because you're iterating backwards.

---

## 4. Two-Player Game DP

A powerful state definition is:

`dp[i] = Current Player's Score - Opponent's Score`

Transition:

`Current Gain - Opponent's Best Advantage`

This naturally models optimal play.

---

## 5. Build the Recurrence in English First

Before writing code, explain the transition:

> "If I make this move, what do I gain, where does the opponent start, and what advantage will they have?"

Then convert that sentence into code.

---

## 6. Use Loops for Repeated Choices

If the problem allows taking **1 to K** items, avoid writing separate cases.

Pattern:

```cpp
sum = 0;
for (int k = 0; k < K && valid; k++) {
    sum += value[i + k];
    // Update answer
}
```

This reduces duplicate code and handles boundaries cleanly.

---

## 7. DP Checklist

Before coding, answer these questions:

1. What is my state?
2. What does `dp[state]` represent?
3. What choices are available?
4. What is the next state after each choice?
5. How do I combine the current choice with the next state's answer?
6. What is the base case?
7. In what order should I compute the states?

---

## Common Mistakes to Avoid

* Choosing the DP type before defining the state.
* Thinking about the history instead of the remaining problem.
* Confusing DP traversal order with state transitions.
* Adding unnecessary DP dimensions.
* Writing repeated transitions instead of using a loop.

---

## Golden Rule

> **The DP state should contain only the minimum information needed to uniquely identify the remaining problem.**
